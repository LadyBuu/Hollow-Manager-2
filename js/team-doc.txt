1. ARCHITECTURE OVERVIEW
================================================================================

The team modules follow a domain-driven design with clear separation of concerns.
Each module has a single, well-defined responsibility.

ARCHITECTURE LAYERS
───────────────────

┌─────────────────────────────────────────────────────────────────────────────┐
│                              UI LAYER                                      │
│  team-manager.js    - Main UI controller, tab rendering, event binding     │
│  team-modals.js     - Modal dialogs (team form, member modal, ranking)     │
│  team-render.js     - Pure rendering (data → HTML)                         │
├─────────────────────────────────────────────────────────────────────────────┤
│                           DOMAIN LAYER                                     │
│  team-core.js       - Canonical mutation API, data validation              │
│  team-members.js    - Member timeline, eligibility, rendering              │
│  team-rankings.js   - Ranking domain logic, cache management               │
│  team-filters.js    - Team filtering semantics                             │
├─────────────────────────────────────────────────────────────────────────────┤
│                           UTILITY LAYER                                    │
│  constants.js       - Shared constants (CALENDAR, STATUS, ID)              │
│  core-utils.js      - Domain utilities (getDisplayName, getCharacterById)  │
│  dom-utils.js       - DOM utilities (escapeHtml, createElement)            │
│  notification.js    - Toast notification system                            │
└─────────────────────────────────────────────────────────────────────────────┘

MUTATION FLOW
─────────────

User Action
    ↓
team-manager.js / team-modals.js
    ↓ (validates UI input)
team-core.js
    ↓ (validates domain rules)
window.data mutation
    ↓
team-manager.js calls saveData()
    ↓
UI refresh (team-render.js, team-list.js)

TEAM-CORE.JS
────────────

PURPOSE: Canonical mutation API for all team data operations.
STATUS: ✅ COMPLETE

RESPONSIBILITIES:
  - Team CRUD (create, read, update, delete)
  - Member operations (add, remove, update)
  - Ranking operations (add, remove, cache management)
  - Data validation (all mutations are validation-atomic)
  - Type normalisation (legacy 'internship' → 'professional')

KEY METHODS:
  - createTeam(teamData) → object|null
  - getTeam(id) → object|null
  - getAllTeams() → array
  - getTeams(type, status) → array
  - updateTeam(id, updates) → object|null
  - deleteTeam(id) → boolean
  - addMember(teamId, memberData) → object|null
  - removeMember(teamId, charId) → boolean
  - updateMember(teamId, charId, updates) → object|null
  - addRanking(teamId, period, rank) → boolean
  - removeRanking(teamId, period) → boolean
  - getActiveMembers(team, period) → array
  - getCurrentRank(team) → string
  - getSortedRankings(team) → array
  - getPeriodDisplay(team) → string
  - getTypeLabel(type) → string
  - getMemberStatusInfo(status) → { label, color }

INVARIANTS ENFORCED:
  - No duplicate members per team
  - Exactly one ranking per period
  - Ranking periods must be valid for team type
  - Member periods must be valid for team type
  - startPeriod <= endPeriod
  - joinPeriod <= leavePeriod (inclusive semantics)
  - Type changes rejected if existing members/rankings invalid

PERSISTENCE CONTRACT:
  - Does NOT call saveData()
  - Caller is responsible for persistence
  - Mutations are applied to window.data immediately

DEPENDENCIES:
  - window.CALENDAR_CONSTANTS
  - window.STATUS_CONSTANTS
  - window.ID_CONSTANTS
  - window.DomUtils
  - window.CoreUtils
  - window.logActivity


TEAM-MEMBERS.JS
───────────────

PURPOSE: Historical timeline engine for team members.
STATUS: ✅ COMPLETE

RESPONSIBILITIES:
  - Determine member status at any period (historical timeline)
  - Determine character eligibility for teams
  - Period-aware candidate selection
  - Render member lists (returns HTML)

KEY METHODS:
  - getStatusAtPeriod(member, period, teamType) → string
  - getStatusAtWeek(member, week) → string
  - getEligibilityStatus(team, char, currentPeriod) → { label, disabled, style }
  - getCandidateCharactersAtPeriod(teamType, period) → array
  - getCandidateCharacters(teamType) → array (current-status based, legacy)
  - renderList(team, filterPeriod) → string
  - parseTypedPeriod(value, teamType) → { value, unit } | null
  - isValidAcademicWeek(value) → boolean
  - isValidYear(value) → boolean

STATUS VALUES RETURNED:
  - 'active':   Member is active at this period
  - 'future':   Member joins at a future period
  - 'left':     Member has left before this period
  - 'deceased': Character died at or before this period
  - 'eliminated': Character eliminated at or before this period
  - 'unknown':  Membership status cannot be determined

PERIOD SEMANTICS:
  - Academic teams: periods are weeks (1-52)
  - Non-academic teams: periods are years (1900-2100)
  - leavePeriod is INCLUSIVE: member remains active during leavePeriod
  - joinPeriod is INCLUSIVE: member becomes active at joinPeriod

ELIGIBILITY HIERARCHY:
  1. If character is already in team → use membership history
  2. If character is deceased → check death year (only for year-based periods)
  3. If character is eliminated → check elimination week (only for week-based periods)
  4. If character is in other team → block (if active or future)
  5. Otherwise → available

PERSISTENCE CONTRACT:
  - READ-ONLY: does NOT mutate data
  - Does NOT call saveData()

DEPENDENCIES:
  - window.TeamCore
  - window.CALENDAR_CONSTANTS
  - window.STATUS_CONSTANTS
  - window.DomUtils
  - window.getCharacterById
  - window.getDisplayName
  - window.getCurrentStatus
  - window.getCharacterAge

────────────────

PURPOSE: Ranking domain logic and rendering.
STATUS: ✅ COMPLETE

RESPONSIBILITIES:
  - Add ranking entries (enforces one per period)
  - Remove ranking entries (exact removal)
  - Maintain currentRank cache
  - Render ranking lists (returns HTML)
  - Ranking queries (getRankAtPeriod, getRankChange)

KEY METHODS:
  - addRanking(teamId, period, rank) → boolean
  - removeRanking(teamId, period) → boolean
  - getSortedHistory(team) → array
  - getCurrentRank(team) → string
  - getMostRecentRanking(team) → object|null
  - getSummary(team) → { total, current, mostRecent, history }
  - hasRankings(team) → boolean
  - getRankAtPeriod(team, period) → number|null
  - getRankChange(team, fromPeriod, toPeriod) → { from, to, change } | null
  - renderList(team) → string
  - renderSummary(team) → string
  - isValidPeriod(period, teamType) → boolean
  - getPeriodRange(teamType) → { min, max, label }

INVARIANTS ENFORCED:
  - Exactly ONE ranking per period
  - Ranks must be positive integers
  - Periods must be valid for team type
  - Malformed entries filtered at query time
  - Mutations reject malformed history (fail-closed)

PERSISTENCE CONTRACT:
  - Does NOT call saveData()
  - Mutations applied to window.data immediately

DEPENDENCIES:
  - window.TeamCore
  - window.CALENDAR_CONSTANTS
  - window.DomUtils
  - window.logActivity


TEAM-FILTERS.JS
───────────────

PURPOSE: Team filtering semantics.
STATUS: ✅ COMPLETE

RESPONSIBILITIES:
  - Filter teams by type and criteria
  - Provide default filter values
  - Read filter values from DOM
  - Build filter HTML (safe, escaped)

KEY METHODS:
  - filterTeams(type, filter) → array
  - getDefaultFilter(type) → object
  - readFilterFromDOM(type, currentState, domRefs) → object
  - buildFilterHTML(type, filter, classes) → string
  - getWeekRange() → { min, max }
  - getYearRange() → { min, max }
  - isValidWeek(week) → boolean
  - isValidYear(year) → boolean

FILTER SEMANTICS:
  - Academic: Teams active during a specific 2-week block (interval overlap)
  - Professional: Teams active during a specific year (interval overlap)
  - Temporary: Teams active during a specific year (interval overlap)
  - Civilian: All civilian teams (no filtering)

PERIOD SEMANTICS:
  - Missing startPeriod = active indefinitely from beginning
  - Missing endPeriod = ongoing (active forever)
  - Active during = interval overlaps the selected period

PERSISTENCE CONTRACT:
  - PURE: no mutation, no persistence

DEPENDENCIES:
  - window.TeamCore
  - window.CALENDAR_CONSTANTS
  - window.DomUtils
  - window.getWeekBlock

TEAM-MANAGER.JS
───────────────

PURPOSE: Main UI controller for team management.
STATUS: ✅ COMPLETE

RESPONSIBILITIES:
  - Render team manager UI
  - Display team lists with filtering
  - Team CRUD operations (delegates to TeamCore)
  - Member management (delegates to TeamCore)
  - Ranking management (delegates to TeamCore)

KEY METHODS:
  - renderTeamManager(container) → void
  - refreshTeamList() → void
  - refreshTeamStats() → void
  - applyFilters(tab) → void

RENDERING PHILOSOPHY:
  - UI refresh happens IMMEDIATELY after mutation, before persistence
  - Memory is authoritative, persistence is best-effort
  - Modals close immediately after successful mutation

PERSISTENCE CONTRACT:
  - Calls saveData() after mutations
  - User notified of persistence failures but UI already shows the change

DEPENDENCIES:

4. API REFERENCE
================================================================================

TEAM-CORE API
─────────────

4.1 createTeam(teamData)
─────────────────────────
Create a new team. Atomic: validates all inputs before mutation.

Parameters:
  teamData (object):
    - name (string, required): Team name
    - type (string, optional): 'academic', 'professional', 'temporary', 'civilian' (default: 'academic')
    - startPeriod (string, optional): Start week/year (empty = open-ended)
    - endPeriod (string, optional): End week/year (empty = ongoing)
    - status (string, optional): 'active', 'inactive', 'deprecated' (default: 'active')
    - nameHistory (array, optional): [{ name, startPeriod, endPeriod }]
    - classId (string, optional): Academic class ID (academic teams only)
    - teamNumber (string, optional): Team number (academic teams only)
    - temporaryMission (string, optional): Associated mission ID

Returns: (object|null) Created team or null if invalid

4.2 getTeam(id)
───────────────
Get a team by ID. Returns a LIVE reference. Do not mutate directly.

Parameters:
  id (string): Team ID

Returns: (object|null) Team object or null

4.3 getAllTeams()
─────────────────
Get all teams. Returns a SHALLOW array copy containing live references.

Returns: (array) Array of team objects

4.4 getTeams(type, status)
──────────────────────────
Get teams filtered by type and status.

Parameters:
  type (string, optional): Team type (normalised internally)
  status (string, optional): 'active', 'inactive', 'deprecated'

Returns: (array) Array of team objects (shallow copy)

4.5 updateTeam(id, updates)
───────────────────────────
Update an existing team. Atomic: validates all updates before applying.

Parameters:
  id (string): Team ID
  updates (object): Fields to update (same schema as createTeam)

Returns: (object|null) Updated team or null if invalid

4.6 deleteTeam(id)
──────────────────
Delete a team permanently. Uses findIndex + splice for exact removal.

Parameters:
  id (string): Team ID

Returns: (boolean) Success

4.7 addMember(teamId, memberData)
─────────────────────────────────
Add a member to a team. Validates all inputs before mutation.

Parameters:
  teamId (string): Team ID
  memberData (object):
    - characterId (string, required): Character ID
    - role (string, optional): Member role (default: 'Member')
    - joinPeriod (string, optional): Join week/year
    - leavePeriod (string, optional): Leave week/year

Returns: (object|null) Added member or null

4.8 removeMember(teamId, charId)
────────────────────────────────
Remove a member from a team. Uses findIndex + splice for exact removal.

Parameters:
  teamId (string): Team ID
  charId (string): Character ID

Returns: (boolean) Success

4.9 updateMember(teamId, charId, updates)
──────────────────────────────────────────
Update a member's details. Atomic: validates complete proposed state.

Parameters:
  teamId (string): Team ID
  charId (string): Character ID
  updates (object): { role, joinPeriod, leavePeriod }

Returns: (object|null) Updated member or null

4.10 addRanking(teamId, period, rank)
─────────────────────────────────────
Add a ranking entry. Enforces one ranking per period.

Parameters:
  teamId (string): Team ID
  period (string|number): Week (academic) or Year (other types)
  rank (string|number): Rank number (positive integer)

Returns: (boolean) Success

4.11 removeRanking(teamId, period)
──────────────────────────────────
Remove a ranking entry by period. Uses findIndex + splice for exact removal.

Parameters:
  teamId (string): Team ID
  period (string|number): Week (academic) or Year (other types)

Returns: (boolean) Success

4.12 getActiveMembers(team, period)
───────────────────────────────────
Get active members of a team at a given period.

Parameters:
  team (object): Team object

4.13 getCurrentRank(team)

Get the current rank for a team. Always recalculates from history.

4.14 getSortedRankings(team)

Get human-readable team type label.

================================================================================
7. PERSISTENCE CONTRACT
================================================================================

GENERAL PRINCIPLE
─────────────────

    ┌──────────────────────────────────────────────────────────────────────────┐
    │  Mutation modules (TeamCore) DO NOT call saveData()                      │
    │  UI modules (TeamManager) DO call saveData()                            │
    │                                                                          │
    │  This separation ensures:                                                │
    │  1. Core modules are testable without persistence side effects           │
    │  2. Persistence can be batched/coalesced by the UI                      │
    │  3. UI controls when persistence happens (after user action)            │
    └──────────────────────────────────────────────────────────────────────────┘

FLOW
────

User Action
    ↓
team-manager.js / team-modals.js
    ↓ (validates UI input)
TeamCore mutation (mutates window.data)
    ↓
team-manager.js calls saveData()
    ↓
UI refresh

EXCEPTIONS
──────────

None. All team mutations follow this contract.

RACE CONDITIONS
───────────────

Not applicable. Mutations are synchronous; persistence is async but
does not block UI updates.


================================================================================
8. SECURITY CONTRACT
================================================================================

XSS PREVENTION
──────────────

All user-controlled data must be escaped before HTML insertion.

Escaping is handled by DomUtils.escapeHtml():

  function escapeHtml(value) {
    return String(value == null ? '' : value)
      .replace(/&/g, '&amp;')
      .replace(/</g, '&lt;')
      .replace(/>/g, '&gt;')
      .replace(/"/g, '&quot;')
      .replace(/'/g, '&#039;');
  }

USAGE PATTERN
─────────────

  // CORRECT ✅
  html += '<span>' + escapeHtml(userName) + '</span>';

  // CORRECT ✅ (DOM API)
  var span = document.createElement('span');
  span.textContent = userName;

  // INCORRECT ❌
  html += '<span>' + userName + '</span>';

CSS INJECTION PREVENTION
────────────────────────

Status colors are hard-coded constants, not user-controlled:

  var map = {
    'active': { label: 'Active', color: 'var(--accent)' },
    'left': { label: 'Former', color: 'var(--text-dim)' },
    // ... all values are hard-coded constants
  };

All CSS values come from trusted sources (variables or constants).


================================================================================
9. MIGRATION GUIDE
================================================================================

LEGACY TYPE MIGRATION
─────────────────────

The type 'internship' is a LEGACY persisted value. It is explicitly migrated
to the canonical 'professional' type on read.

  normalizeTeamType('internship') → 'professional'

This does NOT mutate stored data. Migration is interpretive.

RANKING HISTORY MIGRATION
─────────────────────────

Malformed ranking entries are FILTERED AT QUERY TIME, not repaired during
mutation. This follows the "fail-closed" philosophy:

  - Mutations: reject malformed history (fail-closed)
  - Queries: filter malformed entries (defensive)

EXPLICIT REPAIR
───────────────

For administrative repair of corrupted data, use the repair functions:

  TeamCore repair functions (if available)

This is explicit and does not happen automatically.


================================================================================
10. ERROR HANDLING
================================================================================

MUTATION VALIDATION
───────────────────

All mutations follow this pattern:

  1. Validate inputs (reject invalid)
  2. Validate existing structure (reject malformed)
  3. Build proposed state (clone)
  4. Validate proposed state
  5. Apply mutation

If any step fails, the operation returns null/false and nothing changes.

ERROR RETURN VALUES
───────────────────

  - Object-returning operations: null on failure
  - Boolean-returning operations: false on failure
  - Error messages are logged to console.warn()

UI NOTIFICATION
───────────────

  - showNotification() displays user-facing error messages
  - NotificationSystem is preferred (when available)
  - Fallback to alert() for critical errors

LOG ACTIVITY
────────────

All successful mutations are logged via window.logActivity():

  recordActivity('Created team: ' + team.name + ' (' + team.type + ')');

ERROR: "TeamCore: Data store is not available."
CAUSE: window.data is not defined or window.data.teams is not an array.
FIX: Ensure database.js has loaded and data is ready.

ERROR: "TeamMembers: TeamCore is required but not loaded."
CAUSE: team-core.js must be loaded before team-members.js.
FIX: Check load order in index.html.

ERROR: "TeamManager: TeamCore is required but not loaded."
CAUSE: Same as above.
FIX: Check load order in index.html.

ERROR: "Failed to save team changes to persistent storage."
CAUSE: saveData() failed (IndexedDB error).
FIX: Check IndexedDB availability and permissions.

ERROR: "Duplicate period found in ranking history."
CAUSE: Ranking history contains duplicate periods (malformed data).
FIX: Use repair functions to clean data, or manually remove duplicates.
