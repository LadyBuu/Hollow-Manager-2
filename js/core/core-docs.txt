Here is the consolidated documentation for the core layer, drawing together everything from the rewrites and the verdicts. It's organised as a single document you can drop into `docs/core.md` or the project wiki. Every claim in it matches the shipped code.

# Core Layer

Six modules. Read in this order: **database** → **loader** → **state** → **mutation-pipeline** → **tab-manager** → **bootstrap**. Plus **activity-log**, which any producer may call.

```
┌─────────────┐
│ bootstrap   │  coordinates startup
└──────┬──────┘
       │
       ├─> loader ──> database   (readiness + persistence)
       │
       └─> tab-manager ──> activity-log
                          state
                          mutation-pipeline ──> activity-log
                                             ──> notification (utils)
                                             ──> database.saveData()
```

**Load order in `index.html`** (required by `bootstrap.checkLoadOrder`):

```html
<!-- Utils first; no dependencies among them except leaf ↔ leaf -->
<script src="js/utils/id-utils.js"></script>
<script src="js/utils/object-utils.js"></script>
<script src="js/utils/validation-utils.js"></script>
<script src="js/utils/dom-utils.js"></script>
<script src="js/utils/calendar-constants.js"></script>
<script src="js/utils/calendar-validation.js"></script>
<script src="js/utils/range-utils.js"></script>
<script src="js/utils/format-utils.js"></script>
<script src="js/utils/form-utils.js"></script>
<script src="js/utils/timing-utils.js"></script>
<script src="js/utils/theme-manager.js"></script>

<!-- Core -->
<script src="js/core/activity-log.js"></script>
<script src="js/core/database.js"></script>
<script src="js/core/loader.js"></script>
<script src="js/core/state.js"></script>
<script src="js/utils/notification.js"></script>
<script src="js/utils/modal.js"></script>
<script src="js/core/mutation-pipeline.js"></script>
<script src="js/core/tab-manager.js"></script>
<script src="js/core/bootstrap.js"></script>

<!-- Application -->
<script src="js/app.js"></script>
```

Any deviation from this order causes `bootstrap.js` to dispatch `bootstrapFailed` with a message naming the missing module.

## The three-state model

Three sources of truth, distinguished by **lifetime**:

| State | Lives in | Survives | Owner |
|---|---|---|---|
| **Domain data** | `window.data` | page reload (IndexedDB) | `database.js` |
| **UI state** | `AppState` / `SessionState` | tab switches, not reloads | `state.js` |
| **Readiness** | `DataLoader` internal | the page session | `loader.js` |

Nobody reads `window.data` before `DataLoader.isReady` is true. Nobody persists UI state. Nobody treats readiness as data.

## `database.js` — persistence and migrations

**Data version:** 33. Migrations run in sequence from the stored `_dataVersion` up to 33 on every load. Each migration documents its own purpose and retired fields; the header no longer carries the list.

**Storage:** single IndexedDB store `appData`, keyPath `id`, one row with `id: 'mainData'`. Pre-migration backups are written to `mainData_backup_pre_v<n>` under the same store. Nothing else.

**Public surface** (`window.db`, frozen):

| Method | Purpose |
|---|---|
| `openDatabase` | Open or reuse the IDB connection |
| `ensureDatabaseReady` | Open + memoise; use before first access |
| `loadData` | Read `mainData`, migrate, normalise, return `window.data` |
| `saveData` | Serialise writes; `performSave` in order |
| `getEmptyData` | Fresh empty state (see the schema below) |
| `getDefaultMagicProficiencies` | Default magic block for a character |
| `autoLoadData` | `ensureDatabaseReady` then `loadData`, dispatches `dataReady` |
| `createSafeCopy` | `ObjectUtils.deepClone` wrapper |
| `getDatabaseStatus` | `'uninitialized'` / `'initializing'` / `'ready'` / `'failed'` / `'version-mismatch'` |
| `isDatabaseReady` | Boolean |
| `getLoadError` | Last recorded load error, or `null` |
| `deleteDatabase` | Delete IDB and close |
| `forceReset` | Delete IDB and clear module state (console-only) |

**Also exposed**: `window.loadData`, `window.saveData`, `window.getEmptyData`, `window.getDefaultMagicProficiencies`.

**Side effects at load:** `ensureDatabaseReady().then(autoLoadData)`. `dataReady` is dispatched once (success or failure), 10ms after resolution, on `document`.

### Version mismatch policy

The old code deleted the entire database on `VersionError`. That is gone.

If IndexedDB reports a stored database at a higher `DB_VERSION` than the build requests, `openDatabase` sets `_dbStatus = 'version-mismatch'`, rejects with a `VersionMismatchError`, and logs a message pointing to `window.db.forceReset()`. Data is not wiped.

To recover, the user runs:

```js
await window.db.forceReset();
location.reload();
```

from the console. This is deliberate: destroying user data without their knowledge is worse than a failed load.

### Pre-migration backups

Before the first migration on a store, `writePreMigrationBackup(version, rawData)` writes the *raw* `mainData` payload to `mainData_backup_pre_v<version>`. It only writes if a backup for that version doesn't already exist. On failure, it logs a warning and continues; backup failure does not block the migration save.

This closes the "v19 wipes weeklyTeams, v27 admits to losing assignments" gap: whatever is about to be lost is preserved.

### Class-reference pruning

`normaliseDataStructure` prunes references to non-existent classes for `grades`, `rankings`, `enrolments`, `weeklyTeams`, `classDisciplines`, `socialScores`, and `character.classIds`. This is the correct shape guard for a healthy store.

But pruning is **skipped** when:

- `data._skipClassPrune === true`, or
- `academy.graduatingClasses` is empty.

In both cases a `console.warn` explains why. An empty or half-loaded class map no longer cascades through the reference stores.

### Migration dependencies

v17, v18, v23, v26 require `TournamentSchema`, `IdUtils`, `TeamConstants`, and `CalendarValidation` respectively. If a required module is missing, the migration **throws**, `migrateData` aborts, and `_dataVersion` does not advance. The next load (with the module present) runs the migration properly.

This is the fix for the "warn, skip, but bump version anyway" bug. A migration that cannot run does not pretend to have run.

### Soft dependencies

- `structuredClone` — required (native). No JSON fallback.
- `ObjectUtils.deepClone` — preferred; a local `structuredClone`-only wrapper is used if absent.
- `ValidationUtils.parseStrictPositiveInteger` — preferred; a local equivalent is used if absent.

Missing soft dependencies produce a one-time `console.warn`, not an error.

### Save queue

`saveData` returns a Promise. Concurrent calls are serialised: the first call runs `performSave`, and waiters queue behind it. Each caller resolves or rejects with the outcome of the save that included their changes. A failed save rejects all waiters, dispatches `dataSaveFailed`, and the next queued save starts fresh.

### Schema at version 33

Top-level keys:

```
_dataVersion: 33
characters:     []
teams:          []      // team.periods is the source of truth (v33)
departments:    []
tournaments:    []
missions:       []
activities:     []      // capped at 100, newest first (activity-log.js)
classes:        []
locations:      []
currentYear:    number
currentWeek:    number
curriculum:     {...}   // disciplines, restDays, examDays, grades, etc.
social:         {...}   // relationships + relationshipTypes
statsConfig:    {...}   // classes with statWeights, minStats, icon
academy:        {...}   // graduatingClasses, grades, rankings, enrolments,
                        // socialScores, weeklyTeams, classDisciplines,
                        // teachingGroups, teachingSequences, teachingSessions
```

Retired top-level fields (v1–v33): see the individual migration functions. The header no longer lists them; each migration explains its own.

## `loader.js` — readiness adapter

**Purpose:** translate the `dataReady` event into a callback API, and own the readiness state that other modules query.

The module owns **readiness**, not data. `window.data` is the canonical source; `DataLoader` is the observable that says whether it exists.

**Public surface** (`window.DataLoader`, frozen):

| Member | Type | Purpose |
|---|---|---|
| `isReady` | getter | Boolean |
| `hasFailed` | getter | Boolean |
| `isInitialized` | getter | Boolean |
| `error` | getter | Last error, or `null` |
| `init()` | method | Idempotent; attaches the `dataReady` listener |
| `whenReady(onReady, onError?)` | method | See below |
| `getData()` | method | `window.data` if ready, else `null` |
| `getStatus()` | method | `'uninitialized'` / `'waiting'` / `'ready'` / `'failed'` |
| `getError()` | method | Same as `error` getter |
| `reset()` | method | Clears readiness/error; preserves pending callbacks |
| `retry()` | method | Real retry; see below |

### `whenReady(onReady, onError)`

Both callbacks are optional. Both are invoked **asynchronously** — even if readiness has already resolved. This makes the timing uniform across the fast path and the wait path.

- `onReady(data)` — called with `window.data` on success.
- `onError(err)` — called with the error on failure.

The legacy single-argument form is preserved: if `onError` is not provided and the load fails, `onReady(null)` is called. Callers that check `if (data)` work as before.

### `retry()`

Real retry. Returns a `Promise<data|null>`:

1. If not failed: resolves with `window.data || null`.
2. If failed and a retry is already in flight: returns the same Promise.
3. If failed: resets readiness, calls `db.ensureDatabaseReady()`, calls `db.loadData()`, transitions to ready on success or failed on failure.

If `window.db` is unavailable or missing the required methods, `retry` falls back to a degraded path that waits for a `dataReady` event with a **30-second timeout**. On timeout it marks failed with an honest error rather than hanging forever.

### What loader does *not* do

- It does not touch `window.data`. It observes it.
- It does not treat `window.data`'s presence as a readiness signal on its own. `database.js` assigns `window.data` before the migration save completes, so a naive check would flip `failed` to `ready`. `checkCurrentState` consults `db.getLoadError()` and `db.getDatabaseStatus()` **before** trusting `window.data`.

## `state.js` — UI state

**Purpose:** the single source of truth for UI state — filters, current tabs *within* a feature, expanded rows, selected IDs, etc.

**What it does not hold:** domain data, persistence, navigation (that's `TabManager`).

**Structure:**

```
AppState = {
  dashboard:    {}
  characters:   { filterStatus, filterName, ... }
  teams:        { currentTab, filters: { academic, professional, ... } }
  tournaments:  { currentTournamentId, currentMode, ... }
  curriculum:   { grade, ranking, classView, instructorCalendar, ... }
  missions:     { currentFilter, currentMissionId }
  social:       { selectedCharacterId, viewMode, ... }
}

SessionState = {
  characterListOpen, navOpen, lastTab
}
```

`DefaultAppState` and `DefaultSessionState` are immutable templates. `resetModuleState` and `resetAllState` mutate the live objects **in place**, so callers holding a reference from `getTeamState()` etc. keep a valid reference after a reset.

### Public surface

**State access:**

| Function | Notes |
|---|---|
| `getState(module, key?)` | Live reference. Mutating it bypasses notification. |
| `setState(module, key, value)` | Notifies listeners |
| `updateState(module, updates)` | Applies all keys, then notifies |
| `getModuleState(module)` | Live reference to a module's sub-tree |
| `resetModuleState(module)` | In-place reset; notifies per key |
| `resetAllState()` | In-place reset of all modules |

**Convenience getters:** `getCurriculumState`, `getCharacterState`, `getTeamState`, `getTournamentState`, `getSocialState`, `getMissionState`, `getDashboardState`.

**Curriculum helpers:** `getCurriculumViewWeek(viewName)`, `setCurriculumViewWeek(viewName, week)`. The setter notifies with `(module='curriculum', key=viewName, value=viewObject, oldValue=oldWeek)`.

**Session:** `getSession(key)`, `setSession(key, value)`, `resetSession()`. Session setters notify with `module='session'`.

**Observation:**

```js
var unsubscribe = onStateChange(function(module, key, value, oldValue) {
  // called for each state change
});
```

Listener errors are caught and logged to `console.error`. The listener array is snapshotted before iteration, so a listener that unsubscribes during dispatch does not skip the next listener.

**Debugging:** `getStateSnapshot(includeSession)`, `getStateDiff()`.

### Caveats

- Mutating a value returned by `getState` or a convenience getter bypasses listeners. Use `setState` / `updateState` for tracked changes.
- `setCurriculumViewWeek` emits the module name as the key (not `'viewName.currentWeek'`). Listeners that filter on the key should match `module === 'curriculum' && key === viewName`.

## `activity-log.js` — activity logging

**Purpose:** record user-visible events in `window.data.activities`. Newest-first. Capped at 100.

**Entry shape:**

```
{
  id: string,           // from IdUtils.generateId('act'), or a local fallback
  message: string,      // complete human-readable text
  type: string,         // 'info' | 'success' | 'warning' | 'error'
  timestamp: string,    // ISO 8601
  metadata: object|null // deep-cloned on write
}
```

**Contract:**

- `message` is the **complete text**, not a template. The producer includes any referenced entity names.
- `type` is validated; unknown types are coerced to `'info'`.
- `metadata` is deep-cloned on write. Non-cloneable values are dropped with no error. This defends against a caller storing a function that would break the entire next save via `createSafeCopy`.
- `getHistory()` returns **deep-ish copies**: entries and their metadata are cloned, so a consumer cannot corrupt storage.
- `clearHistory()` empties the array in place (`length = 0`) so holders of `window.data.activities` stay coherent.
- All failures are non-fatal. A missing `window.data` produces a `console.warn` and no entry.

**Public surface** (`window.ActivityLog`, frozen): `record`, `getHistory`, `clearHistory`, `getCount`, `getByType`, `search`.

**Callers:** `mutation-pipeline.js` records entries *inside the mutate phase* (before the save), so the log entry commits atomically with the change it describes. If a save fails and rollback runs, the entry is removed along with the change.

## `mutation-pipeline.js` — transaction orchestration

**Purpose:** every mutation goes through one entry point: validate → snapshot → mutate → log → persist → commit-or-rollback.

**Public surface** (`window.MutationPipeline`):

| Member | Purpose |
|---|---|
| `performMutation(config)` | Enqueue a mutation; returns `Promise<result>` |
| `createSafeBackup(data)` | `ObjectUtils.deepClone` wrapper |
| `saveWithPromise(options)` | `window.saveData()` wrapped so sync throws become rejections |
| `simpleMutation(logMsg, successMsg, failMsg, mutateFn, validateFn?)` | Convenience wrapper |
| `_diagnostic` | Getter/setter for tracing (off by default) |

### `performMutation(config)`

Required:

- `validate(data)` → `{ valid: boolean, message?: string }`
- `mutate(data, backup)` → any (sync or a Promise)

Optional:

- `logMessage` — string or `(result) => string`
- `onSuccess(result)` — called after a successful save
- `onRollback(backup)` — called after a rollback
- `onFailure(error, stage)` — called on validation failure (`stage='validate'`), mutate throw (`stage='mutate'`), or save failure (`stage='save'`)
- `skipLog: boolean` — do not write an ActivityLog entry
- `skipNotification: boolean` — do not show a toast
- `successMessage` — string or `(result) => string`
- `failureMessage` — string
- `_testSaveFailure: boolean` — testing only

Returns `Promise<{ success: boolean, data?: any, message?: string }>`.

### Guarantees

1. **Serialised.** Mutations are queued; only one runs at a time. A failing mutation cannot race another's rollback.
2. **Validate first.** If `validate` returns anything other than `{ valid: true }`, no snapshot is taken, no mutation runs, no log entry is written.
3. **Snapshot is real.** The backup is `ObjectUtils.deepClone(window.data)`, so it is not aliased to live state. Rollback restores it by removing all keys from `window.data` and copying the backup's keys back in.
4. **Log commits with the change.** The ActivityLog entry is written *before* the save. If the save fails, the rollback removes the entry too. The entry and the change it describes are atomic.
5. **Save failure rolls back; post-save failure does not.** The persist step uses `.then(onSaved, onSaveFailed)`. If `onSuccess`, `successMessage(...)`, or the toast throws *after* a successful save, there is no rollback. Only a save failure reverts.
6. **Async mutate is supported.** `mutate` may return a Promise; the pipeline awaits it before proceeding. An async rejection is treated as a mutate-phase failure and rolls back.
7. **Dependencies are lazy.** `ObjectUtils`, `ActivityLog`, `NotificationSystem` are read at call time via accessor functions, not captured at module load.
8. **Dependencies are required.** `checkDependencies()` throws if `window.saveData`, `window.data`, `structuredClone`, `ObjectUtils.deepClone`, or `ActivityLog.record` is missing.

### Diagnostics

`window.MutationPipeline._diagnostic = true` enables trace logging. Off by default. When enabled, `executeMutation` prints the phases and probes for `data === window.data` at the points where a mismatch would be meaningful.

## `tab-manager.js` — navigation and tab lifecycle

**Purpose:** the single source of truth for which tab is active. Features register a render function; `TabManager` owns the DOM switch, the URL hash, and the lifecycle.

**Public surface** (`window.TabManager`, frozen):

| Member | Purpose |
|---|---|
| `register(name, renderFn, unmountFn?)` | Register a tab. `unmountFn` is called when the tab is switched away from. |
| `switchTo(name, replaceHash?)` | Switch tabs. `replaceHash` uses `replaceState` instead of `pushState`. |
| `forceRefresh(name?)` | Re-render the named tab (or the current one) |
| `refreshCurrent()` | `forceRefresh(currentTab)` |
| `getCurrentTab()` | Name or `null` |
| `isTabActive(name)` | Boolean |
| `getTabContainer(name)` | DOM node or `null` |
| `isTabRegistered(name)` | Boolean |
| `getRegisteredTabs()` | Array of names |
| `onTabChange(listener)` | Returns an unsubscribe function |
| `onDataReady(data)` | Called by Bootstrap; requires `data` |
| `destroy()` | Remove listeners, clear registration |

**Lifecycle:**

1. `register(name, renderFn)` is called on script load. Registration is order-independent for the deep-link case (see below).
2. On DOM ready, `TabManager` subscribes to `DataLoader.whenReady`.
3. On ready, `_handleReady()` determines the initial tab: hash > `'dashboard'` > first registered.
4. `switchTo(name)` **renders first, then commits the DOM**. If `renderFn` throws, the DOM is not switched, the hash is not updated, and the error is logged.
5. On switch-away, the previous tab's `unmount` hook runs.

**Deep links:** if the URL hash points to a tab that has not yet registered, `register` recognises the match when it arrives and honours it. This is the fix for "data is ready and dashboard registers before the hash target".

**Hash handling:**

- A tab switch with `updateHistory=true` (the default) uses `pushState`.
- The first navigation of a session uses `replaceState` so Back does not return to an empty hash.
- An empty hash falls back to the current tab without changing the URL.

**Focus and accessibility:** the active tab link gets `aria-selected="true"`, others get `"false"`. Modifier-click (Ctrl, Meta, Shift) and middle-click on a nav link are not intercepted, so "open in new tab" works.

**What `TabManager` does not do:**

- It does not render. Features own their own rendering.
- It does not read `window.data`.
- It does not own "is data ready". `DataLoader` does; `TabManager` observes it.

## `bootstrap.js` — startup coordination

**Purpose:** a single, small coordinator. Load-order check → DataLoader readiness → TabManager.onDataReady → `bootstrapReady`. Or `bootstrapFailed` with a diagnostic.

**Public surface** (`window.bootstrap`, frozen):

| Member | Purpose |
|---|---|
| `init()` | Idempotent. Returns `true` if started or already complete, `false` if in flight or blocked. |
| `reset()` | Clear state and increment the attempt token |
| `reinit()` | `reset(); init()` |
| `getStatus()` | `{ initialized, bootstrapping, resolved, dataReady, dataFailed }` |

**Load-order assertion:** `checkLoadOrder()` verifies that `IdUtils`, `ObjectUtils`, `DomUtils`, `CalendarConstants`, `CalendarValidation`, `DataLoader`, `TabManager`, and `window.db.loadData` are all present with the required methods. If any is missing, `bootstrapFailed` is dispatched with a message naming the missing file. `init` returns `false`.

**Sequence:**

1. `checkLoadOrder()`. If it fails → `bootstrapFailed`.
2. `checkDependencies()`. If it fails → `bootstrapFailed`.
3. Token-guarded attempt.
4. If `DataLoader.isReady` → resolve success.
5. If `DataLoader.hasFailed` → resolve failure and start watching for a retry.
6. Otherwise `whenReady` with both callbacks.

**On success:** `TabManager.onDataReady()` is called. If it throws, `bootstrapFailed` is dispatched (not `bootstrapReady`). Otherwise `bootstrapReady` is dispatched on a **macrotask** so listeners registered by `app.js` (loaded after this file) still receive it.

**On failure:** `bootstrapFailed` is dispatched with the error attached. A second `whenReady` registration watches for a successful retry; if one arrives, `reset()` and `init()` run the sequence again.

**Events:**

```
'bootstrapReady'  detail: { status: 'ready', timestamp }
'bootstrapFailed' detail: { status: 'failed', message, error, timestamp }
```

Both bubble, both cancelable (nobody cancels).

**No safety timeouts.** Bootstrap does not manufacture success. If `DataLoader` never resolves, Bootstrap never fires an event. This is deliberate; a stuck load is surfaced by the loader's own timeout only on the degraded retry path.

## Cross-cutting rules

**1. State ownership.** Domain data lives in `window.data`. UI state lives in `AppState`. Readiness lives in `DataLoader`. Never read across these layers without going through the owner.

**2. Mutation.** Every change to `window.data` goes through `MutationPipeline.performMutation`. Direct writes followed by `saveData()` bypass validation, rollback, and the atomic log.

**3. Logging.** Every mutation logs through `ActivityLog.record`, called from inside the mutate phase. Log messages are complete text.

**4. Save semantics.** `saveData()` returns a Promise and serialises concurrent calls. A failed save rejects all waiters, dispatches `dataSaveFailed`, and does not leave partial state in IndexedDB.

**5. Failure is loud.** Every module that can meaningfully fail logs to `console.error` or `console.warn` with a `[ModuleName]` prefix. Silent catches are reserved for cases where a failure genuinely has no downstream consequence (event dispatch, listener callbacks).

**6. Dependencies are asserted.** `bootstrap.js` asserts load order. `mutation-pipeline.js`, `database.js`, and the utils that require `structuredClone` all check at the point of use and either throw or warn loudly. There is no silent fallback that returns wrong answers.

**7. No JSON clone.** `ObjectUtils.deepClone` and `database.createSafeCopy` use `structuredClone` and throw on failure. There is no JSON fallback anywhere in the save or rollback path.

## Testing the layer

**Smoke checks that the rewrites fix:**

1. **`ObjectUtils.deepClone` on a value containing a function** throws, rather than returning a lossy copy. This is the guard that protects `MutationPipeline`'s rollback.
2. **A second modal opening while a first is showing** does not leave focus stranded; closing the second returns focus to the button that opened the first.
3. **`NotificationSystem.notify('msg', 'success', 3000, fn)`** calls `fn` exactly once, on dismiss.
4. **`ThemeManager.init()` called twice** does not double-bind the toggle button.
5. **`DataLoader.whenReady(cb)` after a failed load** calls `cb(null)`; `TabManager.onDataReady(null)` ignores it; `bootstrapFailed` fires without rendering tabs.
6. **`bootstrap.reinit()` after a failure** does not double-fire `bootstrapReady` from a stale callback.
7. **VersionError** on IDB open does not delete the database. `window.db.forceReset()` does.
8. **A v32 store's first load** writes `mainData_backup_pre_v32` before the migration save.
9. **An empty `academy.graduatingClasses`** does not cascade-prune `enrolments`, `weeklyTeams`, `grades`, `rankings`, `classDisciplines`, or `socialScores`.

**What the layer does *not* test:** rendering, form input, user flows. Those are `app.js` and the feature modules. `bootstrap.js` stops at the moment `TabManager.onDataReady()` returns.

## Change log for this rewrite

Cross-file changes applied in this pass, in the order they were delivered:

1. `activity-log.js` — type coercion, metadata cloning, malformed-entry guards, `getHistory` deep copy, `clearHistory` in place.
2. `state.js` — `resetModuleState`/`resetAllState` in place, listener array snapshot, notify on reset, real key in `setCurriculumViewWeek`.
3. `loader.js` — `whenReady(onReady, onError)`, async callbacks, preserve pending callbacks across reset, degraded-retry timeout, error state precedes `window.data`.
4. `bootstrap.js` — load-order assertion, token-guarded attempts, deferred event dispatch, retry recovery, `onDataReady` throw → `bootstrapFailed`.
5. `tab-manager.js` — render-first-commit-second, live DOM queries, `onDataReady(data)` requires data, unmount hooks, `replaceState` for first nav, `Object.freeze`.
6. `mutation-pipeline.js` — persist/post-process split, log inside the mutate phase, async `mutate`, lazy deps, `_diagnostic` off by default.
7. `database.js` — `deepClone` delegates to `ObjectUtils`, v33 period parser delegates to `ValidationUtils`, VersionError refuses to open, pre-migration backup, class-prune gate, migration dependency throw.
8. `timing-utils.js` — throttle try/finally, debounce `.cancel()`/`.flush()`, `once` rethrows cached error.
9. `id-utils.js` — `Object.create(null)` in `uniqueIds`, `isSameId` requires both valid, `normaliseId` rejects non-finite/boolean, `Object.freeze`.
10. `validation-utils.js` — `truncateString` clamps, `parseNumber('')` returns fallback, `clamp(NaN)` returns `NaN`, `isEmptyObject` narrow, deprecation markers.
11. `object-utils.js` — JSON fallback dropped, dead identity checks removed, `isJsonSerializable` removed, `Object.freeze`.
12. `range-utils.js` — inverted ranges rejected consistently, `undefined` end rejected, self-test fixed, load-order guard fixed.
13. `calendar-validation.js` — strict integer parsing, `parseInRange` returns `null`, missing dep throws, `isValidCalendarDate` uses a leap-year formula, `parseSlot` uses calendar bounds.
14. `format-utils.js` — `CalendarConstants` mandatory, `parseHour` → `parseTimeString`, `getDayNumber` delegates, `formatPercentage` validates decimals, `formatCurrency` fallback per currency.
15. `form-utils.js` — `setFormData` resets by default, checkbox group shape deterministic, disabled controls skipped, `type="number"` uses `valueAsNumber`, event dispatch.
16. `dom-utils.js` — URL scheme allowlist, `on*` refusal, `SafeHtml` marker, `safeHtml` composition, `getData` returns `null`, `sanitizeCssValue` strict.
17. `modal.js` — focus handoff between stacked modals, Escape handled per active modal, focus cache invalidated on show, click-outside guards against drag-release.
18. `notification.js` — `onDismiss` stored on the DOM node, queued dismissals work, refresh preserves duration, `role` set correctly, queue cap.
19. `theme-manager.js` — `init` idempotent, `clearPreference`, `mediaQuery` feature-detect, table-driven toggle, `\uFE0E` variation selectors, `theme-color` meta.

The public API surface of every module is unchanged except for additions (`forceReset`, `flush`, `cancel`, `clearPreference`, `rawHtml`, `destroy`). No caller outside this document needs to change its behaviour to keep working. Callers that depended on documented bugs (e.g. `isSameId('', null) === true`, `formatCurrency` returning `$0` for EUR) will see the fix, which is the intent.
